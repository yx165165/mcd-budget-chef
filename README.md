## 为什么做「口味」这个切口

麦当劳点餐相关的工具，大多在解「这一单怎么最省」。但**点餐决策的真正起点不是价格，是「我今天想吃什么味」**。

官方的 MCP 提供了菜单、营养、价格、优惠券——**唯独没有提供「口味」这个维度**。`query-meals` 返回的是分类和餐品编码，不告诉你「巨无霸是咸鲜带点酸甜、口感多汁」。

所以这个项目做了两件别人没做的事：

1. **建了一份 67 款餐品的口味图谱**（六维口味 + 口感 + 温度），**每一款都附配料依据、可逐条溯源**；
2. **把「口味」变成可计算的向量**，于是「推荐类似的」「按口味描述找」「从历史订单学偏好」这三种需求，都能用同一套相似度机制解决。

## 四大功能

### ① 口味推荐（主功能）

三个入口，都指向同一套口味向量引擎：

```bash
# 入口 A：我喜欢吃巨无霸，找类似的
python src/cli.py recommend --like "巨无霸"

# 入口 B：直接描述想吃什么口味
python src/cli.py recommend --want "想吃甜的，要酥脆的，不要牛肉"

# 入口 C：从我的历史订单学偏好（会自动排除已点过的）
python src/cli.py recommend --history examples/history_sample.txt
```

入口 C 的做法值得说明：它把历史订单里每款餐品的口味向量按**时间加权平均**（越近的订单权重越高），得出你的口味重心；同时按各维度的**方差**调整权重——你在某维度上点的越稳定，说明越挑，该维度权重越高。

> 💡 想先看看跑起来什么样？直接打开[在线演示](https://yx165165.github.io/mcd-flavor-scout/)，
> 它就是这套算法的浏览器版镜像（同一份数据、同一套评分公式）。

### ② 营养配餐

把热量、蛋白质、脂肪、钠纳入硬约束。**数据缺失时如实显示「无」，绝不用 0 或估计值填充。**

### ③ 最优优惠

优惠券与组合**联合搜索**。因为满减券有整单门槛，先挑最便宜的单品再看能不能用券，会漏掉「多花 3 元凑到门槛、反而实付更少」的解。

### ④ 简洁点餐

一句话给一餐，参数全走默认值，不逼你填表。

```bash
python src/cli.py simple "来个辣的汉堡，预算30块"
```

它会自动从这句话里解析出口味（辣）、品类（汉堡）、预算（30 元），并**锁定汉堡类**——否则「最省」会把主食换成更便宜的小食，点出来不像一餐。

### 附：完整方案（三合一）

```bash
python src/cli.py plan --want "想吃辣的" --budget 35 --kcal 900 --min-protein 25
```

输出：口味推荐候选池 → 在池内求解「最省 + 营养达标」的组合 → 给出实付、省了多少、营养明细与逐项达标判定。

## 工作原理

```
        「我想吃点甜的」        「我喜欢巨无霸」       「我的历史订单」
              │                      │                    │
              ▼                      ▼                    ▼
        ┌─────────────────────────────────────────────────────┐
        │ 口味画像 TasteProfile                                │
        │  · text  解析口味词/口感词/忌口 → 目标向量 + 权重      │
        │  · anchor 取基准餐品的向量                            │
        │  · history 时间加权平均 + 方差定权                    │
        └──────────────────────┬──────────────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────────────┐
        │ 相似度检索（口味图谱 67 款）                          │
        │  score = 0.85 × 加权口味接近度                       │
        │        + 0.10 × 口感命中                            │
        │        + 0.05 × 温度命中      （封顶 100%）          │
        └──────────────────────┬──────────────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────────────┐
        │ 口味门槛过滤：只保留 ≥ 最高分 × 0.7 的候选            │
        │ （否则「口味不搭但便宜」的菜会混进最优方案）           │
        └──────────────────────┬──────────────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────────────┐
        │ 组合 × 券 联合枚举                                   │
        │  · 营养硬约束过滤（热量/蛋白/钠）                     │
        │  · 每组合试所有券，取减免最大                         │
        │  · 按实付升序（整数分运算，无浮点误差）                │
        └─────────────────────────────────────────────────────┘
```

## 数据说明（重要，请务必阅读）

本项目有三个数据文件，**性质不同，必须区分**：

| 文件 | 内容 | 性质 |
|---|---|---|
| `data/flavor_tags.json` | 67 款餐品的口味标签 | ⚠️ **基于公开配料信息的结构化推断**，非官方数据。每条附 `evidence` 字段记录依据，可逐条溯源 |
| `data/nutrition_demo.json` | 营养数值 | ⚠️ **离线演示占位数据**，未与官方核验 |
| `data/prices_demo.json` | 价格与优惠券 | ⚠️ **离线演示占位数据**，未与官方核验 |

**真实运行时**，营养与价格应通过麦当劳 MCP 的 `list-nutrition-foods` / `query-meals` / `query-store-coupons` 获取，并用 `calculate-price` 复核金额。程序每次输出都会带数据来源标签，**不会把演示数据冒充官方数据**。

**数据缺失策略**：任何未收录的餐品，程序显示为「无」并明确告知，**绝不用 0 或估计值填充**。（仓库中 `白松露风味法式火腿安格斯厚牛堡` 即为一例缺失，可用于验证该机制。）

## 目标用户

- **口味驱动型消费者**：知道自己爱吃什么味，但说不上来菜单里哪个像；
- **想换换口味又怕踩雷的人**：以喜欢的餐品为锚点，找口味相近的新品；
- **减脂/健身人群**：要控热量蛋白，但不想为此天天吃同一样；
- **预算敏感人群**：想省钱，但不想为了省钱点到不合口味的东西；
- **懒得做选择的人**：一句话点餐，不填表。
