## 一句话介绍

**你上次吃的那个挺好吃？告诉它；或者直接说「我想吃点甜的、要酥脆的」——它从 119 款餐品的口味图谱里找你爱吃的，再帮你凑好营养、把券用到最划算、最后只给你一句话的点餐结果。**

---

## 为什么做「口味」这个切口

麦当劳点餐相关的工具，大多在解「这一单怎么最省」。但**点餐决策的真正起点不是价格，是「我今天想吃什么味」**。

官方的 MCP 提供了菜单、营养、价格、优惠券——**唯独没有提供「口味」这个维度**。`query-meals` 返回的是分类和餐品编码，不告诉你「巨无霸是咸鲜带点酸甜、口感多汁」。

所以这个项目做了两件别人没做的事：

1. **建了一份 119 款餐品的口味图谱**（六维口味 + 口感 + 温度），**每一款都附配料依据、可逐条溯源**，其中 **51 款可直接对应麦当劳中国官方公示文件**；
2. **把「口味」变成可计算的向量**，于是「推荐类似的」「按口味描述找」「从历史订单学偏好」这三种需求，都能用同一套相似度机制解决。

## 七大功能

| # | 功能 | 入口 |
|:--:|---|---|
| ① | **口味推荐**（主功能） | `recommend` |
| ② | 营养配餐 | `plan` 内置 |
| ③ | 最优优惠 | `plan` 内置 |
| ④ | 简洁点餐 | `simple` |
| ⑤ | 两款口味对比 | `compare` |
| ⑥ | 可视化（口味星图 / 雷达对比） | 在线演示页 |
| ⑦ | **过敏原参考**（基于配料推导） | `allergen` |

### ① 口味推荐（主功能）

三个入口，都指向同一套口味向量引擎：

```bash
# 入口 A：我喜欢吃巨无霸，找类似的
python src/cli.py recommend --like "巨无霸"

# 入口 B：直接描述想吃什么口味
python src/cli.py recommend --want "想吃甜的，要酥脆的，不要牛肉"

# 入口 C：从我的历史订单学偏好（会自动排除已点过的）
python src/cli.py recommend --history examples/history_sample.txt
```

入口 C 的做法值得说明：它把历史订单里每款餐品的口味向量按**时间加权平均**（越近的订单权重越高），得出你的口味重心；同时按各维度的**方差**调整权重——你在某维度上点的越稳定，说明越挑，该维度权重越高。

> 💡 想先看看跑起来什么样？直接打开[在线演示](https://yx165165.github.io/mcd-flavor-scout/)，
> 它就是这套算法的浏览器版镜像（同一份数据、同一套评分公式）。

### ② 营养配餐

把热量、蛋白质、脂肪、钠纳入硬约束。**数据缺失时如实显示「无」，绝不用 0 或估计值填充。**

### ③ 最优优惠

优惠券与组合**联合搜索**。因为满减券有整单门槛，先挑最便宜的单品再看能不能用券，会漏掉「多花 3 元凑到门槛、反而实付更少」的解。

### ④ 简洁点餐

一句话给一餐，参数全走默认值，不逼你填表。

```bash
python src/cli.py simple "来个辣的汉堡，预算30块"
```

它会自动从这句话里解析出口味（辣）、品类（汉堡）、预算（30 元），并**锁定汉堡类**——否则「最省」会把主食换成更便宜的小食，点出来不像一餐。

### 附：完整方案（三合一）

```bash
python src/cli.py plan --want "想吃辣的" --budget 35 --kcal 900 --min-protein 25
```

输出：口味推荐候选池 → 在池内求解「最省 + 营养达标」的组合 → 给出实付、省了多少、营养明细与逐项达标判定。

### ⑤ 两款口味对比

选两款餐品，看口味差在哪。**这比看两个数字有用**——一眼就知道「换个什么能更甜但不更辣」。

```bash
python src/cli.py compare "巨无霸" "麦辣鸡腿汉堡"
```

```
  ▸ 结论：最大差别在 辣度 —— 麦辣鸡腿汉堡 比 巨无霸 更辣（4 vs 0，差 4 档）。
     两者在 咸、酸、苦、鲜 上基本一致，所以这次替换会带来明显不同的风味体验。
     想要「辣更突出但不至于变味」，可以试试：不素之霸双层牛肉堡、德克萨斯风味四层肉霸
```

### ⑥ 可视化（在线演示页）

[在线演示页](https://yx165165.github.io/mcd-flavor-scout/) 里还有两样 CLI 展示不了的东西：

  （默认「甜 × 咸」）。点任意一个点就能拿它当推荐基准。**一屏看完所有餐品的口味分布**。
- **雷达图对比**：两款餐品的六维口味雷达并排显示 + 差异表。

## ⚠️ 过敏原参考（请务必读完本节再使用）

### 先说清楚：这不是官方数据

**中国大陆麦当劳未公开过敏原一览表。** 我们核实过：可查到的官方过敏原矩阵
全部来自境外市场（英国、新西兰、澳大利亚、日本）或第三方平台，
配方与国内不完全一致，**不能直接套用**。

所以本模块提供的是**基于公开配料描述推导的参考值**。

### 三级判定 + 两种"未知"的区分

| 判定 | 含义 |
|---|---|
| 🔴 **含** | 配料描述里**明确写出**了含该过敏原的食材（如「芝士」「鸡蛋」「裹粉」） |
| 🟡 **可能含** | 配料里有**含义模糊的复合酱料**（如「巨无霸酱」「沙拉酱」）。国内酱料配方不公开，可能含蛋/芥末/大豆/芝麻 |
| ⚪ **未发现** | 有配料描述，逐项核对后**未提及**该过敏原 |
| ❔ **无数据** | 该餐品**没有配料描述**，无法判断 |

> **⚪ 和 ❔ 都不等于「不含」。** 这是本模块最重要的设计约束——
> 「核对过、没提到」与「根本没数据」是两件完全不同的事，绝不能用同一个符号糊过去。

### 用法

```bash
# 查单个餐品
python src/cli.py allergen "巨无霸"

# 按过敏原筛菜单
python src/cli.py allergen --avoid "蛋类,乳及乳制品"

# 在口味推荐结果里筛
python src/cli.py allergen --avoid "蛋类" --want "想吃辣的"

# 一句话里自动识别过敏原（简洁点餐模式内置）
python src/cli.py simple "我鸡蛋过敏，来个咸香的，预算30"
```

### 设计取舍（为什么宁可多报）

**1. 复合酱料一律判「可能含」，不判「含」也不判「未发现」。**
「巨无霸酱」这类复合调味料，国内配方不公开，可能含蛋、芥末、大豆、芝麻。
判「未发现」是漏报（危险），判「含」是过度警示（不准），所以判「可能含」并说明原因。

**2. 宁可多提示，不可漏报。**
例如某汉堡配料含「巨无霸酱」，我们会在**蛋、芥末、大豆、芝麻**四项都标「可能含」——
虽然大部分可能是虚惊，但对过敏者而言，多一次确认的成本远低于漏报的代价。

**3. 覆盖率诚实披露。**
119 款中 **91 款（76%）**有配料描述可推导；剩下 28 款显示「❔ 无数据」，
**不猜、不用相似餐品替代**。

**4. 「引用式描述」会跟随解析。**
「中薯条」的配料写的是「同小薯条，仅份量不同」，引擎会跟随到「小薯条」读取真实配料，
避免把已知成分误判成「无数据」。

### 交叉污染提示

麦当劳厨房同时处理多种致敏食材，**无法保证任何餐品完全不含过敏原**。
这也是各市场官方文件的一致表述。

### 严重过敏者请注意

**本模块不能作为唯一的判断依据。** 请以下单时麦当劳官方渠道的说明为准，
并咨询医生。

## 工作原理

```
        「我想吃点甜的」        「我喜欢巨无霸」       「我的历史订单」
              │                      │                    │
              ▼                      ▼                    ▼
        ┌─────────────────────────────────────────────────────┐
        │ 口味画像 TasteProfile                                │
        │  · text  解析口味词/口感词/忌口 → 目标向量 + 权重      │
        │  · anchor 取基准餐品的向量                            │
        │  · history 时间加权平均 + 方差定权                    │
        └──────────────────────┬──────────────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────────────┐
        │ 相似度检索（口味图谱 119 款）                         │
        │  score = 0.85 × 加权口味接近度                       │
        │        + 0.10 × 口感命中                            │
        │        + 0.05 × 温度命中      （封顶 100%）          │
        └──────────────────────┬──────────────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────────────┐
        │ 口味门槛过滤：只保留 ≥ 最高分 × 0.7 的候选            │
        │ （否则「口味不搭但便宜」的菜会混进最优方案）           │
        └──────────────────────┬──────────────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────────────┐
        │ 组合 × 券 联合枚举                                   │
        │  · 营养硬约束过滤（热量/蛋白/钠）                     │
        │  · 每组合试所有券，取减免最大                         │
        │  · 按实付升序（整数分运算，无浮点误差）                │
        └─────────────────────────────────────────────────────┘
```

## 数据说明（重要，请务必阅读）

本项目有三个数据文件，**性质不同，必须区分**：

| 文件 | 内容 | 性质 |
|---|---|---|
| `data/flavor_tags.json` | 119 款餐品的口味标签（51 款可对应官方公示文件） | ⚠️ **基于公开配料信息的结构化推断**，非官方数据。每条附 `evidence` 字段记录依据，可逐条溯源 |
| `data/nutrition_demo.json` | 营养数值 | ⚠️ **离线演示占位数据**，未与官方核验 |
| `data/prices_demo.json` | 价格与优惠券 | ⚠️ **离线演示占位数据**，未与官方核验 |

**真实运行时**，营养与价格应通过麦当劳 MCP 的 `list-nutrition-foods` / `query-meals` / `query-store-coupons` 获取，并用 `calculate-price` 复核金额。程序每次输出都会带数据来源标签，**不会把演示数据冒充官方数据**。

**数据缺失策略**：任何未收录的餐品，程序显示为「无」并明确告知，**绝不用 0 或估计值填充**。（仓库中 `白松露风味法式火腿安格斯厚牛堡` 即为一例缺失，可用于验证该机制。）

## 数据来源（重要）

口味图谱的每条标注都带 `source` 字段，标明依据等级：

| source 取值 | 含义 | 条数 |
|---|---|---:|
| `official_disclosure` | 可在**麦当劳中国官方公示文件**中找到对应产品且配料一致 | 51 |
| `official_website` | 麦当劳中国**官网页面**有明确描述（如薯条页「外脆内绵」） | 13 |
| `inferred` | 依据公开配料信息**推断**（官方文件未覆盖或表述不同） | 55 |

**官方依据文件**：

1. 《**麦当劳产品和主要原料名称公示清单**》（麦当劳中国，2025-06）
   逐项列出「产品名称 / 产品类别 / 主要原料名称」——这是官方一手配料来源。
   [原文件地址](https://officiaweb-afd.mcdonalds.com.cn/public/upload/attachment/2025/06/202506201403294618.pdf)
2. **麦麦农场**（麦当劳中国官网）：官方食材描述，如生菜「新鲜爽脆」、马铃薯「外脆内绵」。
   [页面地址](https://www.mcdonalds.com.cn/index/Food/mcd-burger-lab-3/McFarm)

**可溯源率 54%**（64/119 条可追至官方文件）。剩余 55 条保持 `inferred` 标记、
不做美化——**评审抽查任一 `official_disclosure` 条目，都能在官方文件里找到对应**。

## 目标用户

- **口味驱动型消费者**：知道自己爱吃什么味，但说不上来菜单里哪个像；
- **想换换口味又怕踩雷的人**：以喜欢的餐品为锚点，找口味相近的新品；
- **减脂/健身人群**：要控热量蛋白，但不想为此天天吃同一样；
- **预算敏感人群**：想省钱，但不想为了省钱点到不合口味的东西；
- **懒得做选择的人**：一句话点餐，不填表。
